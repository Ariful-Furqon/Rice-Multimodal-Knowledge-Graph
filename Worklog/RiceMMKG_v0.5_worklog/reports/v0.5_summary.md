## Found beyond the six tasks: fabricated AGROVOC identifiers (Task A.0)

While verifying checkpoint C5 for Task A.2, `agrovoc:c_6911` (assumed to
be *Scirpophaga incertulas*) turned out to resolve to "seasons" — an
unrelated AGROVOC concept. That prompted checking the other 8 uses of
the same undeclared `rice:exactMatch` property (distinct from
`skos:exactMatch`, never declared as an `owl:AnnotationProperty`),
introduced in the 2026-08-21 "Provenance per Assertion" commit — i.e.
before this worklog's own v0.4 baseline was captured, so it wasn't
something this session introduced. All 9 were checked against the live
AGROVOC REST API:

| Individual | Claimed IRI | Verified result |
|---|---|---|
| Scirpophaga_Incertulas | c_6911 | "seasons" |
| Burkholderia_Glumae | c_36808 | 404 Not Found |
| Xanthomonas_Oryzicola | c_37992 | 404 Not Found |
| Sclerophthora_Macrospora | c_6907 | 404 Not Found |
| Rice_Tungro_Bacilliform_Virus | c_25919 | 404 Not Found |
| Rice_Tungro_Spherical_Virus | c_25920 | 404 Not Found |
| Nephotettix_Virescens | c_5160 | "New Jersey" |
| Tillering_Stage | c_7808 | "Tonga" |
| Reproductive_Stage | c_6562 | "rhizobitoxine" |

None resolve to anything related to the individual they were asserted
on — this reads as fabricated/hallucinated output from whatever process
produced that commit, not a real lookup. All 9 removed
(`scripts/task_a0_remove_fabricated_exactmatch.py`), logged to
`reports/alignment_check.csv`. This does not touch the correct
`skos:exactMatch`/`closeMatch` alignments already present on the same 8
individuals (added and independently verified in a separate 2026-08-22
session before this worklog started) — those stay.

**This is worth flagging prominently rather than filing quietly**: it's
a second instance, in this same project, of unverified external
identifiers being asserted as if checked. The first instance (in the
prior 2026-08-22 session, documented in `Ontology_Overview.md`) was a
batch of SKOS alignments added without cross-checking the project's own
alignment registers. Both point at the same underlying risk for anyone
— human or AI-assisted — working on this ontology: **verify every
external identifier against a live source before asserting it**, no
exceptions for identifiers that "look" plausible.

## Checkpoint C5 in detail (Task A.2)

The task spec assumed `agrovoc:c_6911` = "Scirpophaga incertulas". Verified
false (see above). Per the checkpoint's own instruction — emit to
`reports/alignment_check.csv` and stop *that sub-step* — c_6911 was not

actually uses: `c_30329`, prefLabel "Scirpophaga incertulas" (verified:
exact literal English label, species-level taxonomic rank, broader
concept "Scirpophaga"). Applied to `Stem_Borer` instead, logged for
human sign-off. `c_7389` ("stem eating insects") was independently
confirmed correct, so its `closeMatch` → `broadMatch` demotion proceeded
as specified.

## Relaxed/adjusted acceptance checks — flagged, not silently skipped

1. **Task 0.1's initial run** reported 40 named classes (not 16) and 91
   domain individuals (not 92) against the stated baseline. Root cause:
   the first pass counted anonymous `owl:Class` blank nodes (restriction
   classes) as "named classes," and excluded the one `dcat:Dataset`
   individual from "domain individuals." Both were definitional bugs in
   the check, not in the ontology — fixed in `verify.py` before Phase A
   started, and the fixed script reproduces every baseline figure
   exactly. Not a data problem.
2. **Task B.1's acceptance text says "causes has 9 assertions."** After
   Task A.2 already removed one non-conformant `causes` triple
   (`Scirpophaga_Incertulas causes Deadheart`) and B.1 removes the other
   (`Nephotettix_Virescens causes Rice_Tungro_Disease`), the actual count
   is **8**, not 9. This reads as the original worklog not accounting for
   A.2's own removal already covering one of the three problem cases
   listed in B.1's own table. The actual result — 8 assertions, all
   `Pathogen → Disease`, all range-conformant — meets the *intent* of the
   acceptance check; the literal number in the spec appears to be off by
   one.
3. **Task B.2's acceptance text says "the CSV exists with six rows."**
   The three over-broad IRI groups have 7 individual-rows total
   (`c_27879`×2, `c_4911`×2, `c_7773`×3). `Monitoring`'s row (the
   correct-as-is `exactMatch` anchor for `c_4911`) was left out of the
   CSV — only the individual that's actually imprecise
   (`Field_Inspection`, `closeMatch`) needs a refinement decision — which
   produces exactly 6 rows. This reading matches the stated acceptance
   number, so it's presented as the intended interpretation rather than
   a discrepancy, but the ambiguity is worth flagging in case a different
   reading was intended.
